# Changelog

Newest entry first. The **Current state** section describes the extension as it is now, not how it got here.

## Current state (last synced 2026-10-31)

- **Commands:** `Coordiner: Check Environment`, `Coordiner: Run Story…` (runs the Story template), `Coordiner: Start…` (a quick pick of templates, single skills and your chains, with the same Run checks as the editor), `Coordiner: Open Chains`, `Coordiner: Stop Run`; a Sessions view in the activity bar (view id `coordiner.run`) lists the open session on top with each step's tier, model, effort and status (a bell and "waiting for you", on the session and on its running step, while that card waits for you or asks you something; the activity bar's Coordiner icon then carries a badge, seen with the view closed), and below it this repo's lines of work, one row per worktree (those git lists on a `coordiner/<slug>` branch and those earlier sessions ran in; the main worktree's, also in a linked worktree's window), most recently active first, each saying how its latest run ended and at which card, its changed files, its commits not in the main checkout's HEAD and when it was last active, or that its folder is gone or no longer a worktree; under a row its sessions, newest first, each with its steps; clicking one runs the hidden `coordiner.openSession`. A row offers **Continue** (when its latest run can be continued), **Start a Chain Here**, **Open in New Window** and **Remove Worktree…**, inline and in its context menu (hidden commands `coordiner.continueWorktree`, `startHere`, `openWorktree`, `removeWorktree`). ▶ (Start…) and the chains editor are in its title bar, and the welcome text (`No sessions yet.`) offers Start… and Open Chains, and a Stop button while the run slot is held or the chat after a run is open (context key `coordiner.busy`). Stop Run stops the run; once it has ended, it ends the chat after it; while the run is still being set up, it says to answer or cancel the open dialog. Under the running step it lists that turn's background processes (shell commands, Monitors, subagents) with their latest progress line, through `plain()` and clipped to 120; **Stop Process** (inline, or the context menu for the keyboard) stops one, acts only on an id in the live list, and logs the task's kind and id, never its description. The list clears when the turn ends.
- **Build and packaging:** `pnpm build` runs `build.ts`, which bundles every dependency into `dist/` with esbuild (only `vscode` is external); the extension and the four modules the chains webview imports from `dist/` stay entry points. The `.vsix` comes from `pnpm dlx @vscode/vsce@4.1.0 package --no-dependencies` and carries no `node_modules`; `src/bundle.test.ts` fails if `dist/` would import anything but `vscode` and Node builtins. `pnpm audit` reads the lockfile only: the Agent SDK's `sdk.mjs` inlines its own zod (4.5.4 in 0.3.292), which ships in `dist/extension.js` unseen by it (profile §Security, accepted risks).
- **Claude Code:** sessions run the `claude` you installed: `coordiner.claudePath`, else the first `claude` on the sessions' PATH, else `~/.local/bin/claude`, else the binary the Claude Code editor extension bundles (`resources/native-binary/claude` in its current folder, so an update of that extension does not break it). The claude and the sessions' environment are read again for every turn (`turnTools`), so a setting fixed while a card waits applies when it carries on. Check Environment checks it first and runs no session without it; Run refuses before asking for input, and the chains palette shows the same message naming the setting.
- **Packaging and identity:** version 0.4.0 (semver; bumped once per release, profile §Deployment), published on the VS Code Marketplace as `matis-dev.coordiner`, with an Open VSX listing for VSCodium (the README's Install section points to both; the `.vsix` build stays for contributors), publisher `matis-dev`, MIT license, repository, issue and keyword links; `.vscodeignore` trims the packaged extension down to `dist/**`, `media/**` and documentation. Marketplace icon (`media/icon.png`, 512×512) and activity bar glyph (`media/coordiner.svg`, 24×24 `currentColor`) share the modern Kammerdiener motif: tuxedo, bowtie and targeting HUD monocle. The chains editor's tab icon is one fixed-colour copy per theme kind (`media/coordiner-light.svg`, `media/coordiner-dark.svg`), because a tab icon is drawn as an image and `currentColor` has nothing to follow.
- **Chains:** a chain is a list of sessions, each a row of skill cards (`skill`, `args`, `label`, `pause`, optional `next`, `model` and `effort`). Every session is a fresh conversation. Four read-only templates ship, named after what you bring: Story, Idea (brainstorming → planning → implementing), Bug (debugging alone, which writes the fix itself) and New project (kickoff → planning → implementing). Six single-skill templates run one m-skills command in one session and ask only for a run name: Kickoff and Onboard (both pause for you), Security audit, UI audit, Accessibility audit and Docs audit. A template is duplicated to edit, and your own chains are saved in `chains.json` in the extension's global storage, never in a repo. A placeholder in a card's arguments sets what Run asks for: `{{story}}` a backlog story or a typed one, `{{idea}}` and `{{bug}}` a typed answer. A chain uses one kind at most (Run refuses more); a chain with none asks only for a run name.
- **Model and effort:** each card has a **Model** select (**By tier**, or one of the models the session lists through `supportedModels()`, stored as the id it resolves to, and named by the lead of its description, "Opus 5.5"; the `default` row is matched last, so it only adds a model no other row resolves to) and an **Effort** select (the levels the card's model takes; on By tier, only those all three tier models take). A pinned model runs every turn of the card, loop turns and the reminder included, and `NEXT <tier>` then only picks the tier of the card after it. A stored model or effort the session does not offer stays selected and marked, and Run is refused before the worktree. If the models cannot be listed, nothing is refused, a pinned model shows as stored, and the session's own model check still guards the turn. `model` must match `MODEL` and `effort` be one of `EFFORTS` (`src/chains.ts`). A **Pause for me** checkbox sets the card's `pause`. On a template, a change to any of the three goes to a copy (`copyThenEdit`, `src/editor-logic.ts`; named by `copyName`), which is selected with focus on the same control and announced as "Copied <template> to <copy> to save this change"; arguments and skills still need **Duplicate to edit**.
- **Chains editor:** a webview (`Coordiner: Open Chains`) with templates, single skills and saved chains in a full-height rail on the left and the selected chain's sessions on the right, a "fresh context" divider between sessions. Cards are numbered as stations in each lane, in a grid whose columns line up from one session to the next. The accent colour is the theme's link colour (`--vscode-textLink-foreground`, falling back to `focusBorder`); the focus ring stays on `focusBorder`. Cards are added from the skills the open folder's Claude Code session offers (listed once per window without a model turn; m-skills first), moved with arrow buttons or Alt+←/→, and edited in place; every change is saved at once. The toolbar puts Run first, then Duplicate (**Duplicate to edit** on a template), with **Delete chain** set apart at the far end; the name is a field in its own row, and **Refresh skills** sits once at the foot of the rail, since the skill list is the window's, not a chain's. A line under the toolbar says what the last edit did: a removed card or session with **Undo** (focus returns to the restored item's Remove button, and "Restored …" is announced), or "Saved as <copy>. Templates don't change." when a setting on a template made a copy; it clears at the next edit or when another chain is picked, and a state from the extension keeps it. A rail entry says **needs m-skills** only while m-skills is missing, on any chain that uses it, your own included. The card a run starts or waits on is scrolled into view when the chat covers it, once per card and state, with focus left where it was. Each chain says what it starts from; a placeholder shows as a chip with what Run will put there, and an editable chain explains the three placeholders, and a card whose arguments hold a `{{…}}` that is none of them (a file path, say) notes that the skill gets it as typed (`strayNote`). A disabled Run says why; while a run is in progress, it names the ways to stop it. Run, **Add**, **Add a session** and a disabled **Effort** also carry their reason as a tooltip. The palette keeps the skill you picked when the editor re-renders. The editor stops at the limits a stored chain holds (30 skills a session, 20 sessions, 20,000 characters of arguments, 100 of name): **Add** and **Add a session** stay focusable but turn off with the reason shown. A `chains.json` that cannot be read is set aside as `chains.json.bak-<time>` and the editor says so; a change that is refused or cannot be written puts the editor back on the saved chains, and each one is announced, even when the reason repeats.
- **Run:** asks for the chain's input. A story is picked from a Markdown backlog file (`## Story N: …` / `### Slice N: …` headings) or typed via **Type a story…**; a file with no such heading runs whole, named by its first heading or, with none, by its file name (`wholeFileStory`), and an empty file is refused; an idea or a bug is typed. A typed answer suggests the run name (its slug, or an empty name when it has no letter or digit in `[a-z0-9]`), which you can change; a picked story is named by its heading. The input is capped at 20,000 characters (heading and body together for a picked story). A chain without a placeholder asks only for a name. A next chain started from the chat after a run (**Start the next chain here**) skips the repository check, the input and the setup: its input is the last reply of the run before, and it runs in that run's worktree, after a modal confirm. First, a folder that is not a git repository, or one with no commits yet, is offered `git init` and a first commit in modals: an empty commit, or every file `.gitignore` lets through, listed by name before it is committed; more than 200 such files are refused, and so is a folder git cannot open (git missing, `safe.directory`), with git's message in the output. A modal confirm lists each session's cards and offers three Run buttons, which set how a question from an unattended card is treated (**Run, wait 5 min for answers**, **Run, wait for my answers**, **Run, never wait**; `RUN_CHOICES`), then a worktree is created at `<repo>.coordiner/<slug>` on branch `coordiner/<slug>` from `HEAD`, and the lockfile-derived install command runs in it. One run at a time: the slot is held from the moment Run is pressed, so a second Run is refused while the first is still asking for its input or installing. The error notifications on the way to a run are not awaited, so one that slides into the notification center cannot keep the slot taken. The backlog file picked last and the Run button chosen last are listed first in this workspace (`lastFirst`, `src/backlog.ts`; `LAST_BACKLOG` and `LAST_WAIT` in `workspaceState`), so Enter picks them again, and a stored value that matches nothing changes nothing. A message about something the output holds offers **Show Output**, and a finished run offers **Open Worktree** (a new window on it) as well (`pointTo`, `src/extension.ts`).
- **Card semantics:** a "once" card takes one turn; `NEXT <tier>` moves to the next card on that tier, `DONE` moves on at the card's own tier. `NEXT` on the last card of a session ends the card as `DONE` does (a kickoff names the planning after it, a step the session does not have). The implementing card is a "loop": it continues on each `NEXT` (tier stops: Heavy/Standard/Light → strong/medium/weak) until `DONE`. A review's `DONE` skips the loop cards after it. A card that pauses for the user (brainstorming, debugging, kickoff, onboard), or one the user paused, talks with them in the run's chat: after each turn it waits, each message is another turn, and **Continue** applies the latest status line it gave (a pausing card that gave none is done). Only unattended turns count toward the 20-turn cap. A card that cannot go on (a `HALT`, a failed turn, no status line after the reminder, the turn cap) parks instead of ending the run: it waits in the chat with the reason, a message is a turn with it (put in front of a prompt that never reached the session), and **Continue** retries it in the session that stopped (`continueAfter`); either move gives it a fresh turn allowance. Stop ends the run with the outcome that parked it.
- **Story template:** session 1 is `planning-architect` → `implementing-architect`; session 2 starts with new files marked intent-to-add (literal pathspecs, cap 200), then `code-review-architect-uncommitted` → `implementing-architect fix the findings` → `rolling-history`. The commit brief is shown in the Coordiner output; nothing is committed.
- **Run chat:** a strip under the chain's detail column (the rail keeps the full height), tied to the run rather than to the selected chain (`media/chat.js`, decisions in `src/chat-logic.ts`, state in `src/talk.ts`, transcript in `src/transcript.ts`, its wiring to the editor and the journal in `src/run-chat.ts`). A divider above it (a focusable separator: drag, or ↑/↓/Home/End) sets its height, 15–80% of the window, remembered in the webview's state (on narrow widths, where the rail stacks above, the chat shrinks to the space left); **Hide chat** folds it to its heading. Until a run starts (phase `idle`) the chat is folded the same way to its heading and status line, with no divider, buttons, transcript or message box, so the chains have the room; a saved height or maximize waits for the run. **Maximize chat** (a toggle button, `aria-pressed`) hides the chains column so the chat fills it, saved as `chatMax`; **Hide chat**, picking a chain in the rail and **New empty chain** un-maximize it. The question form is capped at half the chat and scrolls on its own; the transcript keeps at least three lines. It shows assistant text as Markdown (`markdown`, `src/chat-logic.ts`: headings from h3, paragraphs, emphasis, inline and fenced code, nested and task lists, quotes, tables, rules and links, parsed into plain data and built with `createElement` and text nodes; raw HTML stays text, no image is loaded, only an http(s) address becomes an `href`, no link sits inside another, and a reply over `MAX_MARKDOWN` (50,000) or nested past `MAX_DEPTH` (16) is shown as written), tool calls as the tool's name and the input that says what it did (`toolInput`, `src/transcript.ts`: the command, the file, the questions, the todos; otherwise `key: value` lines; clipped at `MAX_TOOL_INPUT`, 2000) in a box three lines high that scrolls, and a Tab stop only while it scrolls, your messages and answers, grouped by session under a heading whose button (`aria-expanded`) folds the session's entries, with the session's cards as pills beside it (✓ done, ● live, ■ stopped, with the state in words), keeping the newest 1,000 entries (on the page as in the extension) with one note at the top once older ones are dropped; the running card is marked **Running** in its lane, or **Waiting for you** while it waits for you or asks you something (`attention` / `needsYou`, `src/chat-logic.ts`), and a chip by the chat's title says which card works and how long its turn has run (`chipLabel`), or Waiting for you, visible when the chat is hidden. Under the title, the line (`lineOf`, a `nav` labelled Sessions) draws the chain's sessions as numbered stations, each card ✓ done, ● live (`aria-current="step"`), ■ stopped or plain to come, its state also in the button's name; choosing a started session unfolds it and focuses its heading. When a card hands over, a `card-end` row gives its figures on a solid rule, and when a session hands over or the run ends, a `session-end` row gives the session's on the dashed rule, before the next session's heading (`workedLine`: working time summed over its turns, less the time a question waited for you, turns, tokens in with the cached share and out, cost at API prices, then the card's model and effort); "Session N finished" is announced. **Send** during a running turn puts the message into it (below); otherwise, or behind messages already queued, it queues the message in front of the next turn's prompt, with its destination shown and **Withdraw**. While a turn runs, plain text (not a live region) beside the chip shows "last activity m:ss ago · <tool>" from the turn's clock (`TurnClock`, `busyMeta`), and the status line under the head is hidden, since the chip says it; sent answers are announced as "Answers sent; <card> is working on them", and a message that reached a card as "Your message reached <card>". **Pause after this turn** makes an unattended card wait; a skill's AskUserQuestion during a pause is answered in a form (offered labels or Other), which takes focus when focus was in the chat (a lone question is then not also announced; a set of several still announces its count); **Stop run** stops it. A pause or question while the editor is closed opens it without taking focus, with a notification. A question from an unattended card shows in the same form: under **wait 5 min** it counts down in plain text (`expiryLabel`) and the Recommended option is taken when the time runs out, shown as a `decided` entry; otherwise it has no time limit. A parked card's status line says why it stopped, and its Continue reads "Continue <card>", highlighted. Closed fences in assistant text are code blocks with a **Copy** icon in their corner (shown on hover or focus, always on a touch screen; a check mark for 1.5 s after a copy) that sends `chatCopyText`, which the extension only writes to the clipboard, never runs; a block over `MAX_INPUT_CHARS` gets no button, and one with a bidi control or a zero-width character gets a warning instead (`hasHidden`). Every reply and every message of yours has the same **Copy** icon for its text as written (`messageCopy`; one over `MAX_INPUT_CHARS` says it is too long instead), and Ctrl+C / Cmd+C on a selection inside the transcript also sends it as `chatCopyText`, for editors whose webview copy does not reach the clipboard. Queued messages left when the run ends go back to the message box. When the run ends, the transcript gets one line saying how (done, nothing to review, halted with its reason, failed, stopped or refused) and the chat stays open on the run's last session: each message is a turn that resumes it, on its model and effort, with `AFTER_NOTE` (no status line) and the paused-turn tool rules, and each turn holds the run slot, so a new run waits for it. A failed turn is shown in the transcript and the chat stays open. **Stop run** reads **End chat**, Pause and Continue are gone, and **Copy resume command** (`cd <worktree> && claude --resume <id>`, built in the extension) and **Start the next chain here** appear, with **Merge steps** after a run that is done (`canMerge`): it sends `chatMergeSteps`, and the extension reads git now (the worktree must still be listed on its branch) and adds a `merge` entry, not journaled, with numbered steps and a Copy for each command (`mergeSteps`, `src/worktree.ts`: stage in the worktree, the commit brief's commit, `merge --squash`, `commit -C <branch>`, `reset --merge` if it stops on conflicts), or a sentence instead of commands when the main checkout is not on a branch, git cannot say, or nothing is left to merge; focus moves to the entry when it was asked for. The composer's toolbar keeps the other actions on the left and Continue, when shown, then **Send** at the right end (`.toolbar .primary`), so Send never moves. The chat ends when you end it or confirm a new run. While a card waits, a line under the status counts down how long the prompt cache stays warm (one hour or five minutes, read from what each response wrote to the cache; five minutes assumed, and said, until a response shows it), worked out from the clock so a sleep does not skew it, and its expiry is announced once. Paused turns get `INTERACTIVE_NOTE` instead of `UNATTENDED_NOTE`; it says Continue runs only the chain's next skill and ends the run when there is none, so a reply names the next skill without promising Continue runs it. `AFTER_NOTE` says the chat after a run has no Continue and that the next skill starts from **Start the next chain here**.
- **Messages into a running turn:** `runTurn` (`src/session.ts`) sends its prompt as a stream, and `TurnControl.inject` writes a user message into it with priority `now` and a uuid. Observed with Claude Code 2.1.310: the CLI lets the running tool finish, ends the turn there with an empty result, and runs the message as the next turn of the same query, under the same PreToolUse guard and `canUseTool`. `runTurn` skips results while an injected message has not started (the CLI's untyped `command_lifecycle` frames: queued, started, completed, cancelled) and returns the result of the message's own turn, whose status line is the one that counts. A result is skipped only when something accounts for it (the early end each injected message causes, or another command the CLI reported starting), so a CLI that stops sending the frames ends the turn after the message's own turn instead of waiting for ever. `UNATTENDED_NOTE` asks the model to carry on after such a message and still end with its status line; a reply without one gets the usual reminder. `inject` is refused, and the message queued instead, before the session's init, when the init does not list the `msg_lifecycle_v1` capability, and once the turn's final result has closed the stream. A turn that fails or is stopped before an injected message started returns its text as `undelivered`, and `Talk.giveBack` puts it in front of the queue, or back in the message box once the chat has ended.
- **Stops:** a halt or failure the user stops at prints the `claude --resume` line for the session; answers taken without the user are listed under "Decided without you (the Recommended option)"; a stop after the first session also lists the card prompts left to run by hand, from the card that stopped. A run whose review session finds no changed file ends as "nothing to review". A finished run puts its last card's final message in the output, headed "Commit brief" when that card is rolling-history and "Result" otherwise. When the worktree is left unchanged, the output prints `git worktree remove` and `git branch -D` for it, quoted and ready to paste (none when a path holds a control character); Coordiner never runs them.
- **Git guard:** every session carries coordiner's own PreToolUse hook on Bash (`src/guard.ts`): git writes (the plumbing that stages, commits or overwrites files included, and a branch's `-f` / `-t` / `-u` / `--no-track` wherever it sits among the flags), `send-email`, `imap-send` and `svn dcommit`, `--no-verify` / `--no-gpg-sign` and publishing `gh` commands are denied whichever skills the chain uses, and so is anything that can define a git alias for the command: an alias or include set with `-c` / `--config-env`, any `git config` other than a read, and a `GIT_CONFIG*=` assignment. An unreadable command or a hook error is a denial. Denials are logged without the command text. It scans the command text, so it stops accidental writes, not a determined session (a branch named after another flag, a script file, a command built at run time, or an alias in your own git config gets past it); auto mode is the layer behind it.
- **Unattended rules:** permission mode `auto`, any other tool is denied and logged by name and input keys, never input values. Questions follow the run's choice (`QuestionWait`, `src/unattended.ts`): wait 5 minutes (`QUESTION_WAIT_MS`) and then take the Recommended option, wait for the user, or take it at once; a call in which any question has no Recommended option always waits for the user. In a paused turn questions go to the user; every other tool is still decided as unattended. `UNATTENDED_NOTE` keeps `HALT` for what the user must do outside the session (with the commands as fenced blocks, saying which need sudo), makes a reserved decision a question instead, and asks for a `command -v` check before relying on a system tool. A session that ends `success` but flagged as an error (an API error, an outdated `claude`) fails the turn with the text it gave: "the session failed: …". A turn is refused if a skill the chain uses is missing from the session, if a chain using m-skills reports an m-skills load error, or if the model differs from the one requested; each session is capped at 20 turns. m-skills is recommended, not required; Check Environment reports whether it is installed without failing on its absence.
- **Keep awake:** while the run chat can go on without the user (`canGoOnAlone`, `src/chat-logic.ts`: a turn is working, or a question counts down to its Recommended option; this includes a turn of the chat after the run), a helper process blocks system sleep only, never the display, the screen lock or the lid (`keepAwake`, `awakeHelper`, `src/awake.ts`): `systemd-inhibit --what=sleep` on Linux (through `flatpak-spawn --host --watch-bus` from the flatpak), `caffeinate -i` on macOS, PowerShell `SetThreadExecutionState` on Windows. Each helper ends with the extension host. One helper per hold; taking, letting go and a helper that fails or ends on its own are logged in the **Coordiner** output, and the run goes on without the hold. Setting `coordiner.keepAwake` (application scope, on by default).
- **Lines of work:** **Continue** (`continuePoint`, `src/history.ts`) picks up a halted, failed, stopped or closed-mid-run run at the card it stopped at (the card a halted or failed outcome names, else the last one started), in the session that card ran in, on the tier it ran on: a card whose prompt never reached a session is sent it again, one that had already replied is asked for its status line again (`restateAfter`), any other to carry on (`continueAfter` / `pickUpAfter`, `src/run.ts`); `runChain` skips the sessions before it. **Start a Chain Here** runs a picked chain in the worktree with no setup, asking for its input and naming the run after the worktree. Both run only while git lists the worktree on its branch (`stillListed`). **Remove Worktree…** re-lists, then removes the worktree (`--force` only after you agree to lose uncommitted files) and deletes its branch with `-D` (a second confirm names commits HEAD does not have, and says nothing is lost when merging them into HEAD gives HEAD's own tree, as after a squash merge, `landed`; when git cannot count either, nothing is removed), and deletes the journals whose first record names it; it is refused while a run or chat turn goes, while the chat on that worktree is open, and in the window that has it open. For a row whose folder is gone or that git no longer lists, only the journals are removed.
- **Journal:** one JSONL file per run under the extension's global storage (`journal/<slug>-<UTC stamp>.jsonl`), never inside the worktree, and read back by `src/history.ts` for the Sessions list; the first record names the chain, the repo, the worktree and the run's `questions` choice, and holds the chain as picked (`definition`) and its `input`; each `step-started` record carries the step's model, when set its effort, and its `position` (session and card). A continued run writes a `continued` record and goes on in the same file, its step indices following the ones it had. Your chat messages (`you`) and answers (`answer`) are recorded with the card they went to, and answers taken without you as `decided`, with when (`at once` or `after 5 minutes`). Each `step-finished` record carries the turn's `stats` (`ms`, and `usage`: the session's running totals of cost and tokens from the turn's latest SDK result, `spendOf`, `src/session.ts`). What the sessions said is recorded as `entry` (assistant, tool, divider, card-end, session-end and failed entries) and the session each turn ran in as `turn` (session id, model, effort, card, reply); a reopened session appends to its own file.

## 2026-10-30 — feat: Merge steps after a done run, Copy on every message, and no lost-work warning for a squash-merged worktree

- **Merge steps:** after a run that is done, the chat offers **Merge steps** (`canMerge`, `src/chat-logic.ts`; `chatMergeSteps`, no payload). `ChainsEditor.mergeSteps` (`src/extension.ts`) lists the worktrees again, reads the main checkout's branch, the worktree's state and the main checkout's uncommitted files, and adds a `merge` entry (`src/transcript.ts`, not journaled, as it goes stale) whose steps come from `mergeSteps` (`src/worktree.ts`): stage in the worktree, run the commit brief's commit, a squash merge, a commit reusing the branch commit's message (`-C`), and `reset --merge` if the merge stops on conflicts, each value quoted. No commands are printed when git cannot say, the branch is not a `coordiner/<slug>` one, the main checkout is not on a branch, a path or branch has a control character, or nothing is left to merge. Coordiner runs none of them. Focus moves to the entry when it was asked for, not on a reload.
- **Remove Worktree:** `worktreeState` adds `landed` when merging the branch into HEAD gives HEAD's own tree (`merge-tree --write-tree`; a conflict or failure never counts).
