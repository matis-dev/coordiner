# Changelog

Newest entry first. The **Current state** section describes the extension as it is now, not how it got here.

## Current state (last synced 2026-10-28)

- **Commands:** `Coordiner: Check Environment`, `Coordiner: Run Story…` (runs the Story template), `Coordiner: Start…` (a quick pick of templates, single skills and your chains, with the same Run checks as the editor), `Coordiner: Open Chains`, `Coordiner: Stop Run`; a Sessions view in the activity bar (view id `coordiner.run`) lists the open session on top with each step's tier, model, effort and status (a bell and "waiting for you", on the session and on its running step, while that card waits for you or asks you something; the activity bar's Coordiner icon then carries a badge, seen with the view closed), and this repo's earlier sessions below it, newest first, each with how it ended and its steps; clicking one runs the hidden `coordiner.openSession`. ▶ (Start…) and the chains editor are in its title bar, and the welcome text (`No sessions yet.`) offers Start… and Open Chains, and a Stop button while the run slot is held or the chat after a run is open (context key `coordiner.busy`). Stop Run stops the run; once it has ended, it ends the chat after it; while the run is still being set up, it says to answer or cancel the open dialog. Under the running step it lists that turn's background processes (shell commands, Monitors, subagents) with their latest progress line, through `plain()` and clipped to 120; **Stop Process** (inline, or the context menu for the keyboard) stops one, acts only on an id in the live list, and logs the task's kind and id, never its description. The list clears when the turn ends.
- **Build and packaging:** `pnpm build` runs `build.ts`, which bundles every dependency into `dist/` with esbuild (only `vscode` is external); the extension and the four modules the chains webview imports from `dist/` stay entry points. The `.vsix` comes from `pnpm dlx @vscode/vsce@4.0.0 package --no-dependencies` and carries no `node_modules`; `src/bundle.test.ts` fails if `dist/` would import anything but `vscode` and Node builtins. `pnpm audit` reads the lockfile only: the Agent SDK's `sdk.mjs` inlines its own zod (4.5.4 in 0.3.292), which ships in `dist/extension.js` unseen by it (profile §Security, accepted risks).
- **Claude Code:** sessions run the `claude` you installed: `coordiner.claudePath`, else the first `claude` on the sessions' PATH, else `~/.local/bin/claude`, else the binary the Claude Code editor extension bundles (`resources/native-binary/claude` in its current folder, so an update of that extension does not break it). The claude and the sessions' environment are read again for every turn (`turnTools`), so a setting fixed while a card waits applies when it carries on. Check Environment checks it first and runs no session without it; Run refuses before asking for input, and the chains palette shows the same message naming the setting.
- **Packaging and identity:** version 0.2.0 (semver; bumped once per release, profile §Deployment), publisher `matis-dev`, MIT license, repository, issue and keyword links; `.vscodeignore` trims the packaged extension down to `dist/**`, `media/**` and documentation. Marketplace icon (`media/icon.png`, 512×512) and activity bar glyph (`media/coordiner.svg`, 24×24 `currentColor`) share the modern Kammerdiener motif: tuxedo, bowtie and targeting HUD monocle.
- **Chains:** a chain is a list of sessions, each a row of skill cards (`skill`, `args`, `label`, `pause`, optional `next`, `model` and `effort`). Every session is a fresh conversation. Four read-only templates ship, named after what you bring: Story, Idea (brainstorming → planning → implementing), Bug (debugging alone, which writes the fix itself) and New project (kickoff → planning → implementing). Six single-skill templates run one m-skills command in one session and ask only for a run name: Kickoff and Onboard (both pause for you), Security audit, UI audit, Accessibility audit and Docs audit. A template is duplicated to edit, and your own chains are saved in `chains.json` in the extension's global storage, never in a repo. A placeholder in a card's arguments sets what Run asks for: `{{story}}` a backlog story or a typed one, `{{idea}}` and `{{bug}}` a typed answer. A chain uses one kind at most (Run refuses more); a chain with none asks only for a run name.
- **Model and effort:** each card has a **Model** select (**By tier**, or one of the models the session lists through `supportedModels()`, stored as the id it resolves to, and named by the lead of its description, "Opus 5.5"; the `default` row is matched last, so it only adds a model no other row resolves to) and an **Effort** select (the levels the card's model takes; on By tier, only those all three tier models take). A pinned model runs every turn of the card, loop turns and the reminder included, and `NEXT <tier>` then only picks the tier of the card after it. A stored model or effort the session does not offer stays selected and marked, and Run is refused before the worktree. If the models cannot be listed, nothing is refused, a pinned model shows as stored, and the session's own model check still guards the turn. `model` must match `MODEL` and `effort` be one of `EFFORTS` (`src/chains.ts`). A **Pause for me** checkbox sets the card's `pause`. On a template, a change to any of the three goes to a copy (`copyThenEdit`, `src/editor-logic.ts`; named by `copyName`), which is selected with focus on the same control and announced as "Copied <template> to <copy> to save this change"; arguments and skills still need **Duplicate to edit**.
- **Chains editor:** a webview (`Coordiner: Open Chains`) with templates, single skills and saved chains in a full-height rail on the left and the selected chain's sessions on the right, a "fresh context" divider between sessions. Cards are numbered as stations in each lane, in a grid whose columns line up from one session to the next. The accent colour is the theme's link colour (`--vscode-textLink-foreground`, falling back to `focusBorder`); the focus ring stays on `focusBorder`. Cards are added from the skills the open folder's Claude Code session offers (listed once per window without a model turn; m-skills first), moved with arrow buttons or Alt+←/→, and edited in place; every change is saved at once. Each chain says what it starts from; a placeholder shows as a chip with what Run will put there, and an editable chain explains the three placeholders, and a card whose arguments hold a `{{…}}` that is none of them (a file path, say) notes that the skill gets it as typed (`strayNote`). A disabled Run says why; while a run is in progress, it names the ways to stop it. Run, **Add**, **Add a session** and a disabled **Effort** also carry their reason as a tooltip. The palette keeps the skill you picked when the editor re-renders. The editor stops at the limits a stored chain holds (30 skills a session, 20 sessions, 20,000 characters of arguments, 100 of name): **Add** and **Add a session** stay focusable but turn off with the reason shown. A `chains.json` that cannot be read is set aside as `chains.json.bak-<time>` and the editor says so; a change that is refused or cannot be written puts the editor back on the saved chains, and each one is announced, even when the reason repeats.
- **Run:** asks for the chain's input. A story is picked from a Markdown backlog file (`## Story N: …` / `### Slice N: …` headings) or typed via **Type a story…**; a file with no such heading runs whole, named by its first heading or, with none, by its file name (`wholeFileStory`), and an empty file is refused; an idea or a bug is typed. A typed answer suggests the run name (its slug, or an empty name when it has no letter or digit in `[a-z0-9]`), which you can change; a picked story is named by its heading. The input is capped at 20,000 characters (heading and body together for a picked story). A chain without a placeholder asks only for a name. A next chain started from the chat after a run (**Start the next chain here**) skips the repository check, the input and the setup: its input is the last reply of the run before, and it runs in that run's worktree, after a modal confirm. First, a folder that is not a git repository, or one with no commits yet, is offered `git init` and a first commit in modals: an empty commit, or every file `.gitignore` lets through, listed by name before it is committed; more than 200 such files are refused, and so is a folder git cannot open (git missing, `safe.directory`), with git's message in the output. A modal confirm lists each session's cards and offers three Run buttons, which set how a question from an unattended card is treated (**Run, wait 5 min for answers**, **Run, wait for my answers**, **Run, never wait**; `RUN_CHOICES`), then a worktree is created at `<repo>.coordiner/<slug>` on branch `coordiner/<slug>` from `HEAD`, and the lockfile-derived install command runs in it. One run at a time: the slot is held from the moment Run is pressed, so a second Run is refused while the first is still asking for its input or installing. The error notifications on the way to a run are not awaited, so one that slides into the notification center cannot keep the slot taken.
- **Card semantics:** a "once" card takes one turn; `NEXT <tier>` moves to the next card on that tier, `DONE` moves on at the card's own tier. `NEXT` on the last card of a session ends the card as `DONE` does (a kickoff names the planning after it, a step the session does not have). The implementing card is a "loop": it continues on each `NEXT` (tier stops: Heavy/Standard/Light → strong/medium/weak) until `DONE`. A review's `DONE` skips the loop cards after it. A card that pauses for the user (brainstorming, debugging, kickoff, onboard), or one the user paused, talks with them in the run's chat: after each turn it waits, each message is another turn, and **Continue** applies the latest status line it gave (a pausing card that gave none is done). Only unattended turns count toward the 20-turn cap. A card that cannot go on (a `HALT`, a failed turn, no status line after the reminder, the turn cap) parks instead of ending the run: it waits in the chat with the reason, a message is a turn with it (put in front of a prompt that never reached the session), and **Continue** retries it in the session that stopped (`continueAfter`); either move gives it a fresh turn allowance. Stop ends the run with the outcome that parked it.
- **Story template:** session 1 is `planning-architect` → `implementing-architect`; session 2 starts with new files marked intent-to-add (literal pathspecs, cap 200), then `code-review-architect-uncommitted` → `implementing-architect fix the findings` → `rolling-history`. The commit brief is shown in the Coordiner output; nothing is committed.
- **Run chat:** a strip under the chain's detail column (the rail keeps the full height), tied to the run rather than to the selected chain (`media/chat.js`, decisions in `src/chat-logic.ts`, state in `src/talk.ts`, transcript in `src/transcript.ts`, its wiring to the editor and the journal in `src/run-chat.ts`). A divider above it (a focusable separator: drag, or ↑/↓/Home/End) sets its height, 15–80% of the window, remembered in the webview's state (on narrow widths, where the rail stacks above, the chat shrinks to the space left); **Hide chat** folds it to its heading. **Maximize chat** (a toggle button, `aria-pressed`) hides the chains column so the chat fills it, saved as `chatMax`; **Hide chat**, picking a chain in the rail and **New empty chain** un-maximize it. The question form is capped at half the chat and scrolls on its own; the transcript keeps at least three lines. It shows assistant text as Markdown (`markdown`, `src/chat-logic.ts`: headings from h3, paragraphs, emphasis, inline and fenced code, nested and task lists, quotes, tables, rules and links, parsed into plain data and built with `createElement` and text nodes; raw HTML stays text, no image is loaded, only an http(s) address becomes an `href`, no link sits inside another, and a reply over `MAX_MARKDOWN` (50,000) or nested past `MAX_DEPTH` (16) is shown as written), tool calls as the tool's name and the input that says what it did (`toolInput`, `src/transcript.ts`: the command, the file, the questions, the todos; otherwise `key: value` lines; clipped at `MAX_TOOL_INPUT`, 2000) in a box three lines high that scrolls, and a Tab stop only while it scrolls, your messages and answers, and a divider between sessions, keeping the newest 1,000 entries (on the page as in the extension) with one note at the top once older ones are dropped; the running card is marked **Running** in its lane, or **Waiting for you** while it waits for you or asks you something (`attention` / `needsYou`, `src/chat-logic.ts`), and a chip by the chat's title says Working or Waiting for you, visible when the chat is hidden. **Send** during a running turn puts the message into it (below); otherwise, or behind messages already queued, it queues the message in front of the next turn's prompt, with its destination shown and **Withdraw**. While a turn runs, a plain-text line (not a live region) shows "Working m:ss · last activity m:ss ago · <tool>" from the turn's clock (`TurnClock`, `busyLabel`); sent answers are announced as "Answers sent; <card> is working on them", and a message that reached a card as "Your message reached <card>". **Pause after this turn** makes an unattended card wait; a skill's AskUserQuestion during a pause is answered in a form (offered labels or Other), which takes focus when focus was in the chat (a lone question is then not also announced; a set of several still announces its count); **Stop run** stops it. A pause or question while the editor is closed opens it without taking focus, with a notification. A question from an unattended card shows in the same form: under **wait 5 min** it counts down in plain text (`expiryLabel`) and the Recommended option is taken when the time runs out, shown as a `decided` entry; otherwise it has no time limit. A parked card's status line says why it stopped, and its Continue reads "Continue <card>", highlighted. Closed fences in assistant text are code blocks with a **Copy** icon in their corner (shown on hover or focus, always on a touch screen; a check mark for 1.5 s after a copy) that sends `chatCopyText`, which the extension only writes to the clipboard, never runs; a block over `MAX_INPUT_CHARS` gets no button, and one with a bidi control or a zero-width character gets a warning instead (`hasHidden`). Queued messages left when the run ends go back to the message box. When the run ends, the transcript gets one line saying how (done, nothing to review, halted with its reason, failed, stopped or refused) and the chat stays open on the run's last session: each message is a turn that resumes it, on its model and effort, with `AFTER_NOTE` (no status line) and the paused-turn tool rules, and each turn holds the run slot, so a new run waits for it. A failed turn is shown in the transcript and the chat stays open. **Stop run** reads **End chat**, Pause and Continue are gone, and **Copy resume command** (`cd <worktree> && claude --resume <id>`, built in the extension) and **Start the next chain here** appear. The chat ends when you end it or confirm a new run. While a card waits, a line under the status counts down how long the prompt cache stays warm (one hour or five minutes, read from what each response wrote to the cache; five minutes assumed, and said, until a response shows it), worked out from the clock so a sleep does not skew it, and its expiry is announced once. Paused turns get `INTERACTIVE_NOTE` instead of `UNATTENDED_NOTE`.
- **Messages into a running turn:** `runTurn` (`src/session.ts`) sends its prompt as a stream, and `TurnControl.inject` writes a user message into it with priority `now` and a uuid. Observed with Claude Code 2.1.310: the CLI lets the running tool finish, ends the turn there with an empty result, and runs the message as the next turn of the same query, under the same PreToolUse guard and `canUseTool`. `runTurn` skips results while an injected message has not started (the CLI's untyped `command_lifecycle` frames: queued, started, completed, cancelled) and returns the result of the message's own turn, whose status line is the one that counts. A result is skipped only when something accounts for it (the early end each injected message causes, or another command the CLI reported starting), so a CLI that stops sending the frames ends the turn after the message's own turn instead of waiting for ever. `UNATTENDED_NOTE` asks the model to carry on after such a message and still end with its status line; a reply without one gets the usual reminder. `inject` is refused, and the message queued instead, before the session's init, when the init does not list the `msg_lifecycle_v1` capability, and once the turn's final result has closed the stream. A turn that fails or is stopped before an injected message started returns its text as `undelivered`, and `Talk.giveBack` puts it in front of the queue, or back in the message box once the chat has ended.
- **Stops:** a halt or failure the user stops at prints the `claude --resume` line for the session; answers taken without the user are listed under "Decided without you (the Recommended option)"; a stop after the first session also lists the card prompts left to run by hand, from the card that stopped. A run whose review session finds no changed file ends as "nothing to review". A finished run puts its last card's final message in the output, headed "Commit brief" when that card is rolling-history and "Result" otherwise. When the worktree is left unchanged, the output prints `git worktree remove` and `git branch -D` for it, quoted and ready to paste (none when a path holds a control character); Coordiner never runs them.
- **Git guard:** every session carries coordiner's own PreToolUse hook on Bash (`src/guard.ts`): git writes (the plumbing that stages, commits or overwrites files included, and a branch's `-f` / `-t` / `-u` / `--no-track` wherever it sits among the flags), `send-email`, `imap-send` and `svn dcommit`, `--no-verify` / `--no-gpg-sign` and publishing `gh` commands are denied whichever skills the chain uses, and so is anything that can define a git alias for the command: an alias or include set with `-c` / `--config-env`, any `git config` other than a read, and a `GIT_CONFIG*=` assignment. An unreadable command or a hook error is a denial. Denials are logged without the command text. It scans the command text, so it stops accidental writes, not a determined session (a branch named after another flag, a script file, a command built at run time, or an alias in your own git config gets past it); auto mode is the layer behind it.
- **Unattended rules:** permission mode `auto`, any other tool is denied and logged by name and input keys, never input values. Questions follow the run's choice (`QuestionWait`, `src/unattended.ts`): wait 5 minutes (`QUESTION_WAIT_MS`) and then take the Recommended option, wait for the user, or take it at once; a call in which any question has no Recommended option always waits for the user. In a paused turn questions go to the user; every other tool is still decided as unattended. `UNATTENDED_NOTE` keeps `HALT` for what the user must do outside the session (with the commands as fenced blocks, saying which need sudo), makes a reserved decision a question instead, and asks for a `command -v` check before relying on a system tool. A session that ends `success` but flagged as an error (an API error, an outdated `claude`) fails the turn with the text it gave: "the session failed: …". A turn is refused if a skill the chain uses is missing from the session, if a chain using m-skills reports an m-skills load error, or if the model differs from the one requested; each session is capped at 20 turns. m-skills is recommended, not required; Check Environment reports whether it is installed without failing on its absence.
- **Journal:** one JSONL file per run under the extension's global storage (`journal/<slug>-<UTC stamp>.jsonl`), never inside the worktree, and read back by `src/history.ts` for the Sessions list; the first record names the chain, the repo, the worktree and the run's `questions` choice, and each `step-started` record carries the step's model and, when set, its effort. Your chat messages (`you`) and answers (`answer`) are recorded with the card they went to, and answers taken without you as `decided`, with when (`at once` or `after 5 minutes`). What the sessions said is recorded as `entry` (assistant, tool, divider and failed entries) and the session each turn ran in as `turn` (session id, model, effort, card, reply); a reopened session appends to its own file.

## 2026-10-28 · 0.2.0 — feat: Show replies as Markdown, tool calls as what they did, and which card waits for you

- **Markdown replies:** `textParts` is gone. `markdown` / `inline` (`src/chat-logic.ts`, still no runtime import beyond `chains.ts`) parse assistant text into `Block` / `Inline` data, and `media/chat.js` builds it with `createElement` and text nodes only: headings start at h3 under the chat's h2, a table scrolls in its own box, a task's checkbox is disabled and named "done" / "not done". A fence left open stays text, so a half-written block never swallows the rest. Links: the target goes through `new URL` and only `http:` / `https:` becomes an `href` (with the address as its tooltip); any other target is shown in brackets beside the words, an image is never loaded (its description becomes the link's words), and a link's words make no link of their own.
- **Bounded on hostile text:** model text is untrusted, so the parser stays linear in it. Each `[` is matched once per text (`bracketPairs`); a delimiter or a fence whose close was not found is not searched for again from a later point; the fence, heading and table-delimiter checks were rewritten so a long line cannot make them backtrack (`fenceOpen`, `headingText`, `DELIMITER_CELL`); the link and `<…>` patterns are sticky instead of matching a fresh `slice`. Past `MAX_DEPTH` (16) quotes, lists, emphasis and links stay text, and a reply over `MAX_MARKDOWN` (50,000 characters) is shown as written. Measured in node on 49,000-character hostile replies: at most 54 ms each, where the first version took up to 9.9 s on 40,000 and overflowed the stack on 20,000 quote markers or 10,000 brackets.
- **Copy:** the Copy button is a 24×24 icon in the code block's corner, shown on hover or focus (always where there is no hover), with a check mark for 1.5 s after a copy; it keeps its "Copy command N" name, and a block with hidden characters still gets the warning instead.
- **Tool calls:** `toolInput` (`src/transcript.ts`) shows the field that says what a call did (Bash's command, Read's file, Grep's pattern and path, a Skill's name and arguments, AskUserQuestion's questions, TodoWrite's todos as `[x]` / `[~]` / `[ ]`), and `key: value` lines for any other tool; a malformed input (a `null` todo) is shown as written instead of throwing, since a throw in `onMessage` would fail the turn. `MAX_TOOL_INPUT` rose from 300 to 2000 and is shared with `parseJournal`. The input sits in a box three lines high that scrolls; it is a Tab stop, named as a group ("Bash input"), only while it scrolls, checked when entries arrive and again by a `ResizeObserver` when the transcript's size changes, so the keyboard does not pass every tool call on the way to the message box.
- **Waiting for you:** `attention` / `needsYou` (`src/chat-logic.ts`) say whether the card waits for the user (an open question, or waiting during the run; not the chat after a run). The chat's title gets a chip (Working, pulsing in the accent; Waiting for you, in the activity-bar badge colours; no pulse under reduced motion), the lane's flag reads **Waiting for you** (`runningAt.waiting`, `src/editor-protocol.ts`), the Sessions view marks the session and its running step with `bell-dot` and "waiting for you" (`StepView.status` `"waiting"`, `currentItem`'s new phase, `src/view.ts`), and the Coordiner icon in the activity bar carries a badge whose tooltip names the card. `createRunChat` now calls `moved()` when waiting starts or stops, not only on a new card or session.
- **Copy edits:** the Run confirm's notes are shorter (wait modes in one line, still saying that a question with no Recommended option always waits for you); the placeholder note reads "… are placeholders: type one in a card's arguments …".
- **Docs:** README (the chat section: Markdown, tool boxes, the waiting marks and the badge), the profile's §Security (the Markdown controls replace "never rendered as Markdown"), §Deployment (versioning scheme), §Known blind spots and §Recurring Propagation Sites.
- **Tests:** `src/chat-logic.test.ts` (the parser, its bounds, no link in a link, `attention`), `src/chat-dom.test.ts` (rendering, Copy, the chip, tool-input Tab stops with layout and `ResizeObserver` faked), `src/transcript.test.ts` (`toolInput`), `src/run-chat.test.ts` (`moved()` on waiting), `src/view.test.ts`, `src/history.test.ts`, `src/editor-logic.test.ts`, `src/editor-dom.test.ts`.
- **Gates:** `pnpm typecheck`, `pnpm test` (830 tests), `pnpm coverage` (100% lines and functions, 98.84% branches overall; `src/chat-logic.ts` 95.61%, `media/chat.js` 97.54%, `src/transcript.ts` 98.15% branches, so the 100%-branch bar on new code is not met for the parser) and `pnpm build` pass. `pnpm audit` reports 14 advisories (5 high, 7 moderate, 2 low), as before; the lockfile did not change. Not checked in the F5 app: clicking a link in a real webview, the badge, the Markdown and the Copy icon in each theme, and the tool boxes becoming Tab stops with real layout.

## 2026-10-28 — feat: List earlier sessions in the sidebar and reopen their chat after VS Code closes

- **Sessions view:** the Run view is now **Sessions** (same view id, so every `when` clause holds). `SessionsProvider` (`src/extension.ts`) lists the open session on top (its steps, and the running step's processes as before) and this repo's earlier sessions below, newest first, at most 50 (`readNewest` and `listed`, `src/history.ts`), each with how it ended in words and by icon (`sessionItem`, `when`, `currentItem` in `src/view.ts`) and its steps. Rows carry stable ids so expansion survives a refresh. The list loads at start, when a session opens, and when the view becomes visible; only the newest load is shown. The repo is the open folder's `git rev-parse --show-toplevel`; with no folder or no repo the list is empty. `loadSessions` only `stat`s every journal (a file over the size cap is left out there), then `readNewest` parses them newest file first, one at a time, and stops once the repo's newest 50 are in hand, so a journal directory that is never pruned is not read back whole on every refresh; a file's time stands in for its last record's, and `listed` still orders by the latter. The "a run is in progress" reason now names the **Sessions** view's Stop button (`src/editor-logic.ts`).
- **Journal:** two new record kinds, `entry` (assistant, tool, divider, failed: the transcript entries no other record carries; `createRunChat` writes them) and `turn` (the latest session id, model, effort, card and reply; `sessionTurns` writes it each time `last` updates). Existing records are unchanged.
- **Reading it back:** `parseJournal` (`src/history.ts`) rebuilds a run field by field like `parseChains`: bad lines, unknown types and wrong-shaped fields are dropped, text goes through `plain()` again, a session id must match `SESSION_ID` (now exported from `src/worktree.ts`), a model `MODEL`, an effort `isEffort`. The transcript is rebuilt through `Transcript`, so the 1000-entry cap and dropped marker apply. A run with no `outcome` reads as "closed mid-run" and its running step as stopped. A journal from before `turn` falls back to the last finished step's session with an empty reply and is marked `userOnly` ("replies not recorded"). A journal over `MAX_JOURNAL_BYTES` (5 MB) is left out, with one output line.
- **Reopening:** `openSession` re-reads the journal, ends any open chat after a run, seeds `createRunChat({ past })` and, when the worktree exists and a session id was kept, reuses `talkAfter` so sending, End chat, Copy resume and Next chain work unchanged; otherwise the chat opens read-only, with a warning when the worktree is gone. `reopen` runs inside the run slot, so a run cannot start while the journal is read, and the open is refused when the slot is already held; a second click on the row being opened is ignored (`RunState.opening`). Its turns run with no required skills, since a chat turn invokes none. The command's argument is only a key into the current listing, never a path. `runIn`'s turn logic moved to `sessionTurns`, shared with the reopen path.

## 2026-10-10 — feat: Session two and the run journal (slice 2)

- `runStorySession` became `runSession(script, deps)`, driven by a `Script` (`open` turn, `work` loop on `NEXT`, optional `close` turn on `DONE`). `sessionOne(story)` is plan → implement; `SESSION_TWO` is review → fix → history. A `NEXT` in the closing turn counts as a missing status line (one reminder, then halt).
- `runStory` runs session 1, then `prepareReview`, then session 2 as a **fresh** session (never a resume) so the reviewer does not share the author's context. Step numbers continue across both sessions.
- `prepareReview` (`src/worktree.ts`): `git status --porcelain` → `no-changes` on a clean tree; otherwise NUL-separated `ls-files --others --exclude-standard` and `git --literal-pathspecs add --intent-to-add -- …`, so new files appear in `git diff HEAD` without staging their content. More than 200 new files halts the run (usually a missing `.gitignore` entry). `--literal-pathspecs` stops a model-chosen name like `:!src/x.ts` from excluding another file from the review.

- Journal (`src/journal.ts`): `createJournal` writes one JSON line per record in call order; a failed write is reported once and never stops the run.
