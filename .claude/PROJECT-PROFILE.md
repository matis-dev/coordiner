## Identity

- **Project:** coordiner — a VS Code extension that runs chains of Claude Code skills through unattended sessions, each run in its own git worktree, up to the commit brief. The default chain is the user's m-skills story flow; m-skills is recommended, not required.
- **Stack:** TypeScript on Node ≥24, bundled to ESM JavaScript in `dist/` by esbuild (`build.ts`; tsc only type-checks), running in the VS Code extension host (VSCodium 1.135, a flatpak on the user's machine). Built on the Claude Agent SDK, exact-pinned; it is the only runtime dependency. Dev tooling: TypeScript, the node and vscode type definitions, esbuild, commitlint (CLI and the conventional preset), husky, and jsdom with its type definitions (for the webview tests), all exact-pinned.
- **Package manager:** pnpm 12 (`packageManager` pins pnpm@12.15.0 in package.json; lockfile `pnpm-lock.yaml`)
- **Repo shape:** single package, a git repository.
- **Install shape:** run from source through the `Run Coordiner extension` launch config (F5), or installed from a `.vsix` built by `<package>` (§Commands).
- **Node on PATH:** the flatpak editor has no `node`; gates need the nvm Node folder (~/.nvm/versions/node/v24.21.0/bin) and the pnpm folder (~/.local/share/pnpm) put in front of PATH, and sessions get it through the `coordiner.extraPath` setting.

## Conventions

- **Design system / UI vocabulary:** VS Code's own — tree view, quick pick, modal message, output channel, theme icons. The chains webview (`media/editor.css`, `media/editor.js`, and the run's chat in `media/chat.js`) uses native elements and `--vscode-*` theme variables only: no component library, no web fonts.
- **Localized?** no
- **Test layers in use:** unit — `node:test` and strict assert; everything that touches the outside (SDK query, git and install commands, the filesystem) is injected as a parameter and faked in tests. Webview DOM — `src/editor-dom.test.ts` runs the real `media/editor.js` in jsdom against the page `editorHtml` builds, importing the TypeScript sources in `src/` as its sibling modules; it asserts rendering, focus after each edit, status announcements and the messages posted. `src/chat-dom.test.ts` does the same for the run's chat (`media/chat.js`, started by `media/editor.js`). `media/editor.js` exports `start()` so each test page restarts it in one module instance.
- **Test file placement:** next to the source as `src/<name>.test.ts`; the webview scripts' tests are `src/editor-dom.test.ts` (chains) and `src/chat-dom.test.ts` (the run's chat).
- **Coverage bar:** 100% branch on new functions, `media/editor.js` included (`pnpm coverage` includes `media/**/*.js`); `src/extension.ts` (the only file that imports vscode) is the justified exception, covered by the manual F5 smoke.
- **Seam rule:** only `src/extension.ts` imports vscode; every other module is plain TypeScript. `src/chains.ts`, `src/chain-edit.ts`, `src/editor-logic.ts` and `src/chat-logic.ts` also load in the webview from `dist/`, so they take no runtime imports beyond each other. Decisions the webview makes (run reason, missing skill, focus after an edit, Alt+arrow, the running card) belong in `src/editor-logic.ts`, and the chat's (answer checks) in `src/chat-logic.ts`, where they are tested; `media/editor.js` and `media/chat.js` only build the DOM.

## Security

- **Auth model:** n-a — local tool; Claude credentials come from the user's existing Claude Code login.
- **Untrusted input enters at:** model output (final text including the commit brief, AskUserQuestion input, names of files a session creates), headings and bodies of backlog files from a cloned repo, and the repo's lockfiles. Backlog story bodies are passed to the model verbatim by design (size-capped). Since the chains editor: skill names the session lists (`init.slash_commands`, which include a cloned repo's own .claude/skills folder), messages from the chains webview, and the stored chains.json.
- **Controls:** status markers are read from the last line only; story names become branch and directory names only through a strict slug (re-checked before git is called); git and install commands run as argument arrays, never through a shell; the install command is derived from the lockfile and shown in a confirm dialog on every run; model text shown in the UI has control characters stripped; settings are application-scoped so a repo cannot set them; the extension declares untrusted workspaces unsupported; new files are marked for review with intent-to-add, passed after `--` with `--literal-pathspecs` (so a name like `:!other` cannot exclude another file) from NUL-separated `ls-files` output and capped at 200 (`src/worktree.ts` `prepareReview`); the commit brief is shown through `plain()` and never offered as a command to copy or run. Chains: a card's skill must match `^[A-Za-z0-9:_.-]{1,100}$` and be listed in the session's init before a turn runs; stored chains are rebuilt field by field (`src/chains.ts` `parseChains`), and a bad file is set aside, never overwritten, and saves run one at a time through a temp file and a rename (`src/chain-store.ts`); the editor stops at the same limits a stored chain is held to, and a save the extension refuses or cannot write sends the saved state back with the reason, each one announced even when the reason repeats (`unsaved` in `EditorState`); webview messages have an exact key set per type (`src/editor-protocol.ts`) and the m-skills link is a constant, never taken from a message; the webview CSP allows scripts only by nonce or from the extension's own files, and all text is set with `textContent`. Run chat: `chatSend` text is non-empty and at most `MAX_INPUT_CHARS`; `chatAnswer` carries at most four picks of labels (≤1000 chars) and optional Other text, and `Talk.answer` accepts it only for the open question's id and only as offered labels or text marked Other (`checkAnswers`, `src/chat-logic.ts`); a withdraw or answer for an id that is not pending is ignored; chat messages are ignored when no run is going. Model text and tool inputs reach the transcript through `plain()`; a tool's input is cut to the fields that say what the call does (`toolInput`, which shows a malformed input as written rather than throwing) and clipped at `MAX_TOOL_INPUT`, 2000 (`src/transcript.ts`). Assistant text is parsed as Markdown into plain data (`markdown`, `src/chat-logic.ts`) and built with `createElement` and text nodes, never as markup: raw HTML stays text, no image is loaded (its description becomes the link's words), only an http(s) address (checked with `new URL`) becomes an `href`, any other target is shown as text, and no link is put inside another. The parser stays linear in model text: a reply over `MAX_MARKDOWN` (50,000 chars) is shown as written, and nesting past `MAX_DEPTH` (16) stays text, so a hostile reply cannot freeze the webview or overflow its stack. Card model and effort: `model` must match `MODEL` (`^[A-Za-z0-9._:[\]-]{1,100}$`) and `effort` be one of `EFFORTS` (`src/chains.ts` `parseCard`); a stored model or effort the session does not offer is refused at Run (`runReason`), before the worktree; the model reaches the SDK only as an option. Background processes: task descriptions and progress lines reach the Run view through `plain()` and `clip(…, 120)` (`processItem`); `coordiner.stopProcess` acts only on an id in the live list (`liveProcess`), and a stop is logged as the task's kind and id, never its description (`stopLine`, `src/processes.ts`). Paused turns keep `auto` mode and the git guard; only AskUserQuestion goes to the user (`interactiveCanUseTool`). Commands in model text: closed fences become code blocks in `markdown` (`src/chat-logic.ts`) and are set with `textContent`; `chatCopyText` carries non-empty text of at most `MAX_INPUT_CHARS` and is only written to the clipboard (`actOnChat`), never run; a block with a bidi control or a zero-width character gets a warning and no Copy button (`hasHidden`, `src/chat-logic.ts`), since `plain()` keeps those characters; the unattended note asks a halting session to say which commands need sudo.
- **Journal read back (2026-10-28):** the Sessions list and `openSession` read journal files in the extension's global storage with `parseJournal` (`src/history.ts`): files over `MAX_JOURNAL_BYTES` (5 MB) are skipped, each line is parsed in a try, records are rebuilt field by field (unknown types and wrong shapes dropped), text goes through `plain()` again, and a session id (`SESSION_ID`), model (`MODEL`) and effort (`isEffort`) must match before they reach `resume` or the SDK. A journaled worktree path must exist before the chat opens and is shown through `plain()`; `resumeCommand` refuses a control character in it. `coordiner.openSession`'s argument is only a key into the current listing, never a path. Reopened turns keep auto mode, the git guard and `interactiveCanUseTool`, and run with no required skills.
- **Lines of work (2026-10-29):** the Sessions rows come from `git worktree list --porcelain -z` (`listWorktrees`, `src/worktree.ts`; NUL-separated, so a path with a newline stays whole), only for branches matching `coordiner/<slug>`, never the main worktree; the repo root is the main worktree that listing names, so a linked worktree's window reads the same rows. A worktree action takes the row object the tree passed, and only a row in the current listing is acted on (`worktreeRow`). Before running in a worktree (Start a Chain Here, Continue) git must list it now for its repo on the same branch (`stillListed`); Open in New Window opens only a path git listed. Remove (`removeWorktree`) re-lists first, refuses a branch outside `coordiner/<slug>` before git is called, passes the path after `--`, adds `--force` only when the user agreed to lose uncommitted files, and deletes the branch with `-D` only after a second confirm when it has commits the main checkout's HEAD does not; when git cannot count either, nothing is removed (fails closed). It is refused while a run or chat turn holds the slot, while the chat on that worktree is open, and for the worktree open in the window. Journals are deleted by the worktree their first record names, with file names from the journal directory only (`journalsOf`, `deleteJournals`). Continue rebuilds the journaled chain field by field (`parseChainShape`, `src/chains.ts`), checks each step's position against it, and resumes only a `SESSION_ID`, which now cannot start with a dash; the continued run passes the same Run checks (`runReason`, `runnable`) as any other.
- **Unattended session permissions:** `permissionMode: "auto"`; anything auto mode will not approve is denied and logged by tool name and input keys, never input values, since the log goes into the journal (no one is there to answer; `denyTool`, `src/unattended.ts`). Questions follow the run's choice (`QuestionWait`): wait 5 minutes (`QUESTION_WAIT_MS`), then take the Recommended option; wait for the user; or take it at once. A call in which any question has no Recommended option is never answered without the user (fails closed, `unattendedCanUseTool`). Each answer taken without the user is logged, journaled as `decided` and listed in the output when the run ends.
- **Run figures (2026-10-30):** a turn's spend comes from the SDK result's `total_cost_usd` and `modelUsage` and is kept only when every figure is a finite count (`spendOf`, `src/session.ts`); `card-end` / `session-end` journal entries are rebuilt field by field on read-back (card `plain()` ≤1000 chars, status in `STEP_STATUSES`, model `MODEL`, effort `isEffort`, every figure a finite count, `workedOf`, `src/history.ts`) and reach the page only through `textContent`.
- **Merge steps (2026-10-30):** `chatMergeSteps` carries no payload (an extra key is refused); `ChainsEditor.mergeSteps` (`src/extension.ts`) takes the worktree from the extension's own after-run state, never from the page, lists the worktrees again and acts only on one git still lists on the same branch, and only reads git (`currentBranch`, `worktreeState`, `changedFiles`). `mergeSteps` (`src/worktree.ts`) prints commands for the user and never runs them: every path and branch goes through `quote()`, the branch must match `coordiner/<slug>`, a control character in the root, worktree path or target branch prints no commands, and the commit message reaches git only as `commit -C <branch>`, never as text. Any case git cannot answer prints a sentence instead of commands (fails closed). The `merge` entry is not journaled and reaches the page only through `textContent`, its commands through the same Copy as a reply's code blocks (`hasHidden` still applies).
- **Squash-merged worktrees (2026-10-30):** `landed` (`src/worktree.ts`) is true only when `merge-tree --write-tree HEAD refs/heads/<branch>` prints a full object id equal to `HEAD^{tree}`; a conflict, an old git without `--write-tree` or any failure reads as not landed, so Remove keeps the lost-work confirm. It changes only the second confirm's words, never whether it is asked.
- **Sleep block (2026-10-30):** `coordiner.keepAwake` (application-scoped, on by default) holds a helper process that blocks system sleep only (never the display, the screen lock or the lid) while `canGoOnAlone` (`src/chat-logic.ts`) is true for the run chat. `awakeHelper` (`src/awake.ts`) builds its argument array from constants and the extension host's pid; `startHelper` (`src/extension.ts`) spawns it with no shell and `stdio: "ignore"`, so no model, repo or user text reaches it. It ends with the extension host (pid watch, or `--watch-bus` from the flatpak). It fails open: a missing or refused helper is logged once and the run goes on.
- **Git guard:** every session coordiner starts carries its own PreToolUse hook on Bash (`src/guard.ts`, the rules of the m-skills scripts guard-mutations.sh and guard-outward.sh, which live in the m-skills repo): git writes (the plumbing that stages, commits or overwrites files too: `update-index`, `commit-tree`, `read-tree`, `checkout-index`, and `branch -f` / `--force` / `-t` / `--track` / `--no-track` / `-u` / `--set-upstream-to` wherever they sit among the flags, `reflog expire` / `delete`, `sparse-checkout` changes), `send-email`, `imap-send`, `svn dcommit`, `--no-verify` / `--no-gpg-sign` and publishing `gh` commands are denied whichever skills a chain uses, and so is anything that can define a git alias for the command: an alias or include set with `-c` / `--config-env` (key case ignored), any `git config` other than a read (`--get*`, `--list`, `get`, `list`), and a `GIT_CONFIG*=` assignment. It scans the command text, so it stops accidental writes, not a determined session: a branch named after another flag (`git branch -q new`, left open because `--contains X` reads the same), a script file that runs git, a command assembled at run time, an alias from the user's own git config, or a config file the session edits directly gets past it, and auto mode is the layer behind it. It fails closed: an unreadable command or an error inside the hook is a denial. Denials are logged without the command text.
- **Fail-closed rule:** refuse to run a turn if a skill the chain uses is absent from the init message (and, for a chain using m-skills, if m-skills reports a load error), or if the session runs a different model than requested.

Check the layout at ≤560px wide with the chat at its 80% maximum: the rail stacks above the workspace there, and a chat that cannot shrink pushes its composer off the page. Model and effort per card, the cache line and the process rows (2026-10-23) are verified only by unit and jsdom tests: unverified against the real SDK are that a pinned `resolvedModel` id passes the init model check, what the SDK does with an effort a model does not take, that `supportedModels()` answers in the prompt-less listing session, that the CLI forwards `usage.cache_creation`'s `ephemeral_1h` / `ephemeral_5m` counts (without them every cache line reads "assumed 5-minute cache"), and whether background tasks outlive the turn's query (the list is cleared when the turn settles). The tree's inline Stop action is named by its command title, "Stop Process", not per process. The parser's speed bound is measured in node: `markdown` on 49,000-character hostile replies took at most 54 ms there; the webview's own timing is not measured. The session notes in `src/protocol.ts` tell the model which chat buttons exist and what they do, and no test ties that wording to when `media/chat.js` shows each button: after changing a button's visibility or effect, re-read `INTERACTIVE_NOTE` and `AFTER_NOTE` (2026-10-30: after a stopped run, replies told the user to press a Continue the chat no longer showed). The sleep block (2026-10-30) is verified only on Linux: `systemd-inhibit` takes and releases it (checked with `--list`), but that KDE's idle timer honours a `sleep`-only block is unconfirmed until the manual idle check, and the macOS (`caffeinate`) and Windows (PowerShell `SetThreadExecutionState`, value written in decimal) helpers were never run. Coordiner itself is untested on Windows: `findClaude` looks for `claude`, not `claude.exe`.
- **Coordinator state lives outside target repos.** The per-story journal is JSONL in the journal folder of the extension's global storage (`<slug>-<UTC stamp>.jsonl`), and saved chains are chains.json in the same storage. Neither is ever in a worktree, because `code-review-architect-uncommitted` would review it as a change.

## Recurring Propagation Sites

- `JournalRecord` and `Entry` are now also read back by `parseJournal` (`src/history.ts`): a new record kind, a changed field on `RunEvent`, `Outcome` or `Entry`, or a changed `QuestionWait` must be handled there (an unhandled kind is dropped silently). `src/view.ts` `sessionItem` and `media/chat.js` `entry()` read the same shapes.
- Continue (2026-10-29): `run-started.definition` / `input`, `step-started.position`, the `continued` record and `Outcome.at` are read by `parseJournal` into `PastRun.lastCard` (`src/history.ts`), which `continuePoint` turns into a `StartPoint` for `runChain` / `runSessionAt` (`src/run.ts`) and `worktreeItem` (`src/view.ts`) names as the card it stopped at. A continued run appends to the same journal with step indices offset by the steps it had (`runIn`, `src/extension.ts`), which `parseJournal`'s `index === steps.length` check relies on. A new way for a run to stop (an outcome, or a stop before a card starts) needs a case in `lastCard`; the prompts it picks are `continueAfter`, `pickUpAfter` and `restateAfter` (`src/run.ts`).
- Run chat webview (2026-10-30): `createRunChat` posts its first `chat` message while Talk is still `idle`, already carrying the run's `ChatView` fields (`line`, `title`). Anything `media/chat.js` caches across renders must be keyed on what it drew, not on the view's fields, and a DOM test for it must open with `phase: "idle"` before the `running` update, as `src/chat-dom.test.ts` "came idle with the chain" does.
- The Sessions rows' `contextValue`s (`worktree`, `worktree-continue`, `gone`, set in `SessionsProvider.sessionTreeItem`, `src/extension.ts`) are matched by the `when` clauses of the four worktree commands in `package.json` `menus`; the `WorktreeList` shape from `listWorktrees` is read by `loadLines`, `stillListed` and `removeWorktree`.

- Planner tiers (Light, Standard, Heavy) map to the user's strong, medium and weak models in `src/protocol.ts`; the `COORDINER:` status-line grammar lives in `src/protocol.ts` (parser and the unattended note) and must change together.
- The m-skills command strings live in `src/chains.ts` (`SKILL_DEFAULTS`: kind, tier, label and continuation per skill, and `doneSkipsLoops` on the review; `TEMPLATES`) and `src/session.ts` (`REQUIRED_COMMANDS`, which defines "m-skills installed"). They change together with `UNATTENDED_NOTE` in `src/protocol.ts`, which tells each skill how to end its turn, and with the card semantics in `src/run.ts` (`runSessionAt`, `remainingCommands`).
- `Chain` / `Card` in `src/chains.ts` are stored (chains.json in global storage, `parseChains` / `serializeChains`), sent to the webview (`src/editor-protocol.ts` `EditorState`, `media/editor.js`) and edited there (`src/chain-edit.ts`): a field change touches all four.
- `JournalRecord` in `src/journal.ts` embeds `RunEvent` and `Outcome` from `src/run.ts`: a shape change there changes the journal format.
- `INTERACTIVE_NOTE` and `UNATTENDED_NOTE` (`src/protocol.ts`) name the same status lines and change together with `parseStatus` and the pause loop in `runSessionAt` (`src/run.ts`).
- `Card.model` / `Card.effort` (`src/chains.ts`, with `EFFORTS` and `MODEL`) are also read by `runSessionAt` (`src/run.ts`, the model and effort of each turn), `effortChoices` / `runReason` (`src/editor-logic.ts`), `modelOptions` / `commonEfforts` (`src/skills.ts`) and the card's selects in `media/editor.js`; the `step-started` `RunEvent` carries the effort into the journal and `StepView`.
- `QuestionWait` (`src/unattended.ts`) is chosen by `confirmRun` (`src/extension.ts`), which also remembers the last one in `workspaceState` (`LAST_WAIT`) and puts it first, journaled on `run-started` (`src/journal.ts`), passed to `createRunChat` and read by `forTurn` (`src/run-chat.ts`); its wording is in `runNotes` (`src/extension.ts`) and the README's run steps. `QUESTION_WAIT_MS` is restated as "5 min"/"5 minutes" in `DecidedAfter`, `RUN_CHOICES`, `runNotes` and the README.
- A parked card: `runSessionAt` (`src/run.ts`) passes `parked` to `Talk.waitForYou` → `TalkSnapshot.parked` → `statusLine`, `continueLabel`, `announcement` (`src/chat-logic.ts`) → `media/chat.js` (Continue's highlight); the retry prompt is `continueAfter` (`src/run.ts`), and the HALT rule it relies on is in `UNATTENDED_NOTE` (`src/protocol.ts`).
- `MAX_MARKDOWN` and `MAX_DEPTH` (`src/chat-logic.ts`) are restated as "50,000" and "16" in §Security above, and `MAX_MARKDOWN` in the README's chat section. The `Block` / `Inline` shapes `markdown` returns are built into the DOM by `media/chat.js` `markdown()` / `inline()`: a new node type needs a case there.
- `ChatView.cache` (`CacheClock`, `src/chat-logic.ts`) is set by `createRunChat` from each response's usage (`cacheFrom`, `src/run-chat.ts`) and counted down in `media/chat.js` `showCache`.
- The run chat's state: `TalkSnapshot` (`src/talk.ts`) → `ChatView` / `ChatMessage` (`src/editor-protocol.ts`) → `media/chat.js` and `src/chat-logic.ts`; webview → host chat messages are parsed in `src/editor-protocol.ts` and acted on by `actOnChat` (`src/run-chat.ts`), which `createRunChat` also wires to the journal and the editor. The webview's saved state (`vscode.getState`) holds the selected chain and the chat height; `media/editor.js` and `media/chat.js` both write it through `remember`, which merges. `Entry` (`src/transcript.ts`) is rendered in `media/chat.js` `entry()`. A field change touches all of them.
